# K-Gganbu 3-시스템 설계 — 앱 · 백오피스 · 파트너 포털

> 작성: 2026-07-28
> 상위: `PLANNING.md`(기획) · `BUSINESS_STRATEGY.md`(BM) · `PRODUCT_REQUIREMENTS.md`(PRD)
> 목적: 여행자 앱만으로는 돌아가지 않는 **공급(파트너)** 과 **운영·의사결정(백오피스)** 을
> 하나의 데이터 위에서 유기적으로 묶는다. 세 시스템의 경계·책임·데이터 계약을 여기서 확정한다.

---

## 1. 왜 3개인가 — 각 시스템의 존재 이유

| 시스템                           | 사용자                                   | 존재 이유                                                     | 없으면 벌어지는 일                                |
| -------------------------------- | ---------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------- |
| **앱** (모바일, RN)              | 방한 여행자                              | 수요 — 통역·지도·AI·쿠폰으로 여행을 돕고 사용 데이터를 만든다 | 제품이 없다                                       |
| **파트너 포털** (모바일 우선 웹) | 제휴 매장 사장·직원                      | 공급 — 쿠폰을 올리고, QR을 검증하고, **송객 효과를 확인**한다 | 쿠폰 인벤토리가 0 → BM 스토리 A·D 단절(§2)        |
| **백오피스** (PC 웹)             | 내부 팀(PO·MD·마케팅·데이터·사장·시스템) | 운영·의사결정 — 지표를 보고 무엇을 더할지 정한다              | 데이터는 쌓이는데 아무도 못 본다 → 개선 루프 없음 |

**핵심 원칙**: 세 시스템은 **같은 Supabase 데이터 하나**를 본다. 화면만 다르고 진실은 하나다.
집계·권한은 전부 서버(Edge Function + RLS)에서 끝내고, 어느 화면도 자기만의 계산 규칙을 갖지 않는다.

## 2. 상호 보완 관계 (데이터 순환)

```
     [앱] 여행자                         [파트너 포털] 매장
       │  쿠폰 발급·QR 제시                    │  QR 검증(사용 처리)
       │  스탬프 스캔 / 후기·사진               │  쿠폰 등록·수정
       │  걸음·이동·챌린지                      │  송객 리포트 열람
       ▼                                      ▼
  ┌──────────────────────────────────────────────────┐
  │  Supabase (단일 진실)                             │
  │  analytics_events · coupon_issues · stamp_visits │
  │  points_ledger · reviews · feed_* · landing_events│
  └──────────────────────────────────────────────────┘
                         ▲
                         │ 집계·조회(관리자 게이트)
                         │ 쿠폰/파트너 등록·푸시 발송·신고 처리
                  [백오피스] 내부 팀
```

**순환 고리 3개**

1. **공급 → 수요**: 파트너가 쿠폰을 올리면 앱 홈·지도·AI 카드에 딜 배지가 붙는다(`matchDeal`).
2. **수요 → 공급**: 앱에서 QR 사용·스탬프 방문이 발생하면 파트너 포털의 송객 리포트 숫자가 오른다.
   → **파트너에게 "돈이 되는 증거"** 가 생기고, 그게 다음 파트너 영업의 재료가 된다(수익원 2).
3. **양쪽 → 백오피스 → 양쪽**: 백오피스가 퍼널을 보고 문제 구간을 찾아 앱 기능(PO)·딜 구성(MD)·
   채널(마케팅)을 조정한다. 조정 결과가 다시 1·2로 흐른다.

## 3. 백오피스 — 역할별 기능정의 (PC)

> PC는 **정보 밀도**가 무기다. 한 화면에서 비교·판단이 끝나야 한다(스크롤로 찾지 않게).
> 역할 탭은 "누가 무엇을 결정하는가" 기준으로 나눈다. 지표는 전부 서버 집계 API 하나에서 온다.

### 3.1 사장 (경영) — `overview`

| 블록   | 지표                                                      | 결정                   |
| ------ | --------------------------------------------------------- | ---------------------- |
| 북극성 | **여행 1건당 쿠폰·티켓 사용 건수**(BM§7)                  | 제품이 돈을 버는가     |
| 성장   | 신규 사용자·활성 사용자(7일)·재방문                       | 마케팅 예산            |
| 수익   | 쿠폰 사용 건수 × 추정 수수료, 티켓 아웃링크               | 목표 대비 진척         |
| 리스크 | **포인트 부채**(미사용 잔액)·일 발행량, AI 호출량(변동비) | 발행 캡·모델 티어 조정 |

### 3.2 PO (제품) — `product`

- **전환 퍼널**: `coupon_list_view → coupon_tap → coupon_qr_issued → (coupon_issues.used_at)`
  각 단계 수·전환율·이탈 구간. 이탈이 큰 구간이 다음 스프린트 대상.
- **기능별 사용량**: AI 질문/응답, 통역 세션, 스탬프, 챌린지 완주, 게임 — 기능이 실제로 쓰이는가.
- **리텐션 프록시**: 챌린지 연속일 분포, 재방문(활동일 30일 공백 기준) — BM 스토리 C 검증.
- **품질**: 신고 건수, 실패 이벤트.

### 3.3 MD (머천다이징) — `merchandising`

- **파트너·쿠폰 인벤토리**: 파트너 수, 활성 쿠폰 수, 좌표 없는 파트너(딜 매칭 불가 → 보정 대상).
- **딜 성과 표**: 쿠폰별 노출→탭→발급→사용, **사용률**로 정렬 → 부진 딜 교체·상위 노출 판단.
- **카테고리 밸런스**: food/cafe/beauty/activity 분포 — 특정 카테고리 쏠림 감지.
- 액션: 파트너 등록, 쿠폰 등록/중지.

### 3.4 마케팅 — `growth`

- **채널 유입**: `landing_events`의 `ch` 별 방문(크루즈 터미널 QR·게임 공유 등) → CAC 0 채널 검증(BM E2).
- **푸시**: 대상 조회(전체/복귀 유도) + 발송, 발송 이력.
- **공유 바이럴**: 게임 공유 링크 유입(`ch=game_share`).

### 3.5 데이터 분석가 — `data`

- **일별 시계열**: 이벤트·발급·사용·적립을 날짜별로. 기간 선택.
- **CSV 내보내기**: 화면의 표를 그대로 내려받아 외부 분석. (원시 개인식별자는 내보내지 않음)
- **정의 문서 링크**: 지표 정의를 화면 안에 붙여 "이 숫자가 뭐냐"는 질문을 없앤다.

### 3.6 시스템 관리자 — `system`

- **사용량 상한**: `usage_counters`(AI·음성)의 오늘 소진량 — 429 발생 전 감지.
- **신고 큐**: `content_reports` 처리(REQ-UGC-3).
- **알림 기기**: `device_tokens` 등록 수(플랫폼별).
- **데이터 위생**: 오래된 위치 핑, 소멸 예정 포인트 배치 상태.

## 4. 파트너 포털 — 기능정의 (모바일 우선 반응형)

> 매장 사장·직원은 **카운터에 서서 폰으로** 쓴다. PC 백오피스를 축소하면 안 되고,
> "지금 손님 앞에서 할 일"이 첫 화면 최상단에 있어야 한다.

| 우선순위 | 화면            | 내용                                                   | 왜                                           |
| -------- | --------------- | ------------------------------------------------------ | -------------------------------------------- |
| 1        | **QR 검증**     | 카메라 스캔 → 즉시 사용 처리 결과(성공/이미 사용/무효) | 손님을 기다리게 하지 않는 유일한 실시간 업무 |
| 2        | **오늘 요약**   | 오늘 사용 건수 · 스탬프 방문 수 · 최근 사용 시각       | "오늘 장사에 도움이 됐나"를 3초에            |
| 3        | **송객 리포트** | 최근 7/30일 방문·순 방문자, 쿠폰별 발급/사용           | 재계약·송객비 협상의 근거(수익원 2)          |
| 4        | **내 쿠폰**     | 활성 쿠폰 목록·중지, 신규 등록(간단 폼)                | 공급을 파트너가 직접                         |
| 5        | 매장 정보       | 주소·좌표 상태(딜 매칭 가능 여부)                      | 좌표 없으면 앱에 안 뜬다는 사실을 알려야 함  |

**권한**: 파트너는 **자기 매장 데이터만** 본다. 관리자 키를 파트너에게 주지 않는다(§6).

## 5. UI/UX 원칙

**공통**

- 브랜드 팔레트 일치(앱 `@/theme/tokens`와 같은 색): Sky Blue=정보/네비, Coral=쿠폰/행동, Teal=번역, Amber=포인트.
- 숫자는 항상 **비교 대상과 함께**(전일/전주 또는 전환율). 단일 숫자는 판단을 못 만든다.
- 빈 상태에 다음 행동을 넣는다(앱 UX 원칙과 동일 — 막다른 화면 금지).

**백오피스(PC)**

- 좌측 역할 내비 + 상단 기간 선택. 역할 전환 시 기간·필터 유지.
- 카드형 KPI 4개 + 표 1~2개가 기본 레이아웃. 표는 정렬 가능, 상위 20행 + CSV.
- 위험 신호(포인트 부채 급증·상한 근접·신고 누적)는 색이 아니라 **위치**로 알린다(상단 고정 배너).

**파트너(모바일)**

- 첫 화면 = 큰 스캔 버튼. 한 손 엄지 도달 범위(하단 40%)에 주요 액션.
- 카메라 권한 거부 시 수동 코드 입력 폴백(현장에서 실패하면 안 됨).
- 글자는 최소 15px, 결과는 색+아이콘+텍스트 3중 표기(밝은 매장 조명 대비).

## 6. 권한·보안 모델

| 주체              | 인증                                                                 | 접근 범위                  |
| ----------------- | -------------------------------------------------------------------- | -------------------------- |
| 여행자(앱)        | Supabase Auth(Guest/Google/LINE/Phone)                               | 본인 데이터(RLS)           |
| **파트너**        | 매장별 **접근 코드**(partner_access_codes) 또는 관리자가 매핑한 계정 | **자기 partner_id 범위만** |
| 내부 팀(백오피스) | `ADMIN_EMAILS` JWT(Google 로그인) 또는 `ADMIN_API_KEY`               | 전체(집계·운영 액션)       |

- 파트너에게 `ADMIN_API_KEY`를 주지 않는다 — 코드가 유출되면 전체 파트너 데이터가 노출된다.
- 파트너 요청은 `partner-portal` Edge Function이 코드 → partner_id 로 해석하고,
  **모든 쿼리에 partner_id 조건을 서버에서 강제**한다(클라이언트가 보낸 partner_id를 신뢰하지 않음).
- 백오피스 집계는 개인식별자를 반환하지 않는다(사용자 id·이메일 미노출, 집계·마스킹만).

## 7. 구현 매핑

| 산출물       | 경로                                | 비고                                                         |
| ------------ | ----------------------------------- | ------------------------------------------------------------ |
| 백오피스(PC) | `web/backoffice.html`               | 역할 탭 6개, 정적 파일 + Edge Function 호출                  |
| 파트너 포털  | `web/partner.html`                  | 모바일 우선 반응형, 접근 코드 로그인                         |
| 기존 Admin   | `web/admin.html`                    | 유지(쿠폰 등록·검증·푸시) — 백오피스가 상위 집합이 되면 흡수 |
| 집계 API     | `supabase/functions/backoffice`     | 관리자 게이트, 역할별 섹션 반환                              |
| 파트너 API   | `supabase/functions/partner-portal` | 접근 코드 인증, partner_id 강제                              |
| 파트너 코드  | `partner_access_codes` 테이블       | 코드 해시 저장·회전 가능                                     |

호스팅은 기존과 동일(GitHub Pages `gh-pages` 브랜치). 배포 절차는 `SETUP_EXTERNAL.md` 참조.
